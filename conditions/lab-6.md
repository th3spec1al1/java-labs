Для выполнения этого задания ваша система автосалона уже должна представлять собой микросервисную архитектуру с:

- Доменной моделью и бизнес-логикой (ЛР1);
- REST API + PostgreSQL + Liquibase (ЛР2);
- Spring Security + Keycloak (ЛР3);
- Асинхронным взаимодействием через брокер + Outbox (ЛР4);
- Синхронным взаимодействием через gRPC (ЛР5).

Данное задание предполагает повышение observability и надёжности уже существующих процессов, используя только те инструменты и подходы, которые уже применялись на курсе

## Цель задания

- Закрепить навыки работы со Spring Boot, REST API и межсервисным взаимодействием;
- Довести до конца требование сквозной корреляции и наблюдаемости, заявленное в ЛР4; 
- Усилить проверку надёжности уже реализованных процессов.
## ТЗ

### 1. Сквозная корреляция запросов

В ЛР4 уже требовалось наличие traceId в событиях. Необходимо довести этот механизм до полноценного сквозного прохождения через все точки взаимодействия:

1. Реализовать генерацию traceId на входе в систему в REST-контроллере OrderService, если он не передан клиентом в заголовке;
2. Пробрасывать `traceId` в:
	- HTTP-ответ;
    - события, публикуемые в брокер;
    - gRPC-вызовы между OrderService и StorageService;
3. Добавить traceId в MDC для логирования, чтобы он автоматически попадал в каждую строку лога;
4. Настроить паттерн логирования так, чтобы traceId отображался во всех логах обоих сервисов.

### 2. Эндпоинт проверки состояния

Реализовать средствами уже используемого Spring Web простые REST-эндпоинты в каждом сервисе:
1. GET /api/v1/health - возвращает статус сервиса и доступность ключевых зависимостей:
    - Подключение к собственной БД;
    - Для OrderService - доступность StorageService по gRPC.
2. Эндпоинт должен быть доступен без аутентификации, остальные требования безопасности ЛР3 сохраняются.

### 3. Тесты

Дополнить тестовое покрытие, проверив краевые случаи, заявленные в ЛР4–ЛР5, но обычно слабо покрытые:

1. Идемпотентность обработки сообщений: повторная доставка одного и того же события из брокера не должна приводить к повторной смене статуса заказа (тест на дубликат сообщения).
2. Outbox Pattern: проверить, что событие не публикуется, если транзакция изменения статуса заказа откатилась.
3. Отказоустойчивость gRPC: тест, подтверждающий возврат 503 Service Unavailable при недоступности StorageService.

## Нефункциональные требования

1. Новые технологии и библиотеки использовать запрещено;
2. Сохраняется вся бизнес-логика ЛР1 и требования безопасности ЛР3.
